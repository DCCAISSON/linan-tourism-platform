# 导游小程序与原始需求复核

核对日期：2026年10月9日。本文依据需求方原始材料及当前源码，区分实现、发布和真实业务验收；不以历史检查通过代替当前渠道实收。

后续已按用户要求补入照片视频、学生评价、参加人日报及整体隐私中的肖像说明，见[补齐说明](./导游工作台补齐与肖像说明-20261009.md)。下文“本轮”保留首轮工作台交付范围。

## 本轮范围

用户确认补充小程序“我的 → 导游工作台”，优先实现我的团期、本车点名和执行记录。原稿 S39《详细需求整理与确认稿》H01（P81）明确导游主要用手机工作；H02、H03要求本人车辆与参与全团名单、按已确认名单逐人点名。这不是从参考截图推断出的新增需求。

本轮功能包括：

- 使用后台分配的工作人员账号登录；首次临时密码须修改，家长微信登录不能替代工作人员权限。
- 读取已指派团期、本车人员及参与团期的全团简要只读名单。
- 按日期与计划节点逐人点名，记录早餐、午餐、晚餐、查房；未配置节点时可增加实际发生的临时记录。
- 更正记录须填写原因，保留原始记录和历史；已有版本变化时刷新核对。
- 对本车人员记录普通、安全及其他现场事件。
- 后台与小程序使用同一套执行数据，不另建手机名单。页面离开后清空名单与填写内容；本机不保存密码、名单及健康正文。

本轮不把个人健康原文、个人日报编辑、学生评价和照片视频上传迁入小程序。这些对应的后台入口继续保留。

## 管理员和导游如何使用

1. 管理员在“工作人员账号”创建独立账号，授予“查看导游执行”；需要填写者再授予“填写导游执行”，并设置相应团期范围。无需向导游交付管理员账号。
2. 在“执行管理”选择团期，指派导游及负责车辆。“全团查看”只有只读名单能力，不获得本车点名权限。
3. 完成正式人车安排并确认。报名、分车有变化导致确认失效时，先重新核对确认，再继续填写。
4. 导游在新版小程序“我的”进入“导游工作台”，首次使用前确认隐私说明，输入工作人员账号。临时密码更新后重新登录。
5. 进入“我的团期”，选择日期和节点，为本车人员填写实际状态。没有填写的记录不会被自动视为已到、正常用餐或完成查房。
6. 填错时选择“更正”，填写原因并保存。网络失败时先查看页面结果；如提交成功但回读失败，刷新核对后再处理，避免重复记录。
7. 管理员在原有执行管理页面读取、审核和导出记录；家长可见摘要继续依照原有审核与家庭权限规则。

导游手机会话与家长会话分开；退出导游账号不删除家庭账号或订单。账号停用、到期、密码重置、指派撤销后，后续请求仍受后台校验。

## 技术验证与发布边界

证据集中保存在 `.omo/evidence/guide-miniapp-20261009/`。原生工作人员使用显式会话头，网页仍使用原有 Cookie 和来源校验；小程序请求不借用网页来源或家长凭证。该处理与 [uni-app请求文档](https://zh.uniapp.dcloud.io/api/request/request) 关于小程序不能自动保持 Cookie 的说明相符。

已通过：小程序497项测试、API单元712项、独立MySQL数据库HTTP回归35项，以及类型检查和限定代码检查。数据库回归覆盖工作人员原生登录、改密、停用和到期、混合凭证拒绝、原后台登录及执行范围控制。测试库使用合成人员并已删除，没有向生产名单写入测试记录。独立代码审查未发现阻断问题。

这项功能涉及后端认证和小程序页面，需部署对应后端并上传新小程序版本，普通后台内容保存不能让旧小程序自动出现新入口。实际构建、部署、上传结果以本轮发布回执为准。

开发者工具和隔离数据库验证不等于导游真机首团验收。正式使用前，指定导游应以实际账号在手机完成一次登录、点名、记录及后台核对；订阅实收、客服双向收发、保险回执和第三方相册仍按各自真实结果登记。
