## 目标判断

内部工期从用户明确授权的时刻 `T0` 起算，并按Codex连续执行、三条代码线并行和持续集成安排：

- `T+4小时`：完成仓库基线、Node与pnpm环境以及三端脚手架；
- `T+12小时`：贯通课程/团期、多孩报名、服务端计价、模拟支付、名单统计和Excel导出；
- `T+24小时`：当前已确认范围代码完整，三端可运行并完成首次全链路集成；
- `T+48小时`：完成自动测试、浏览器/小程序实际操作、权限及支付异常验证；
- `T+72小时`：完成阻断缺陷修复、部署回滚演练和独立复核，形成UAT候选版；
- `T+3—5天`：在所需业务资料和账号及时提供的条件下形成稳定版。

`T+24小时`表示当前已确认范围达到代码完整，不等同于正式生产开放。未确认的业务规则不得猜测，真实微信支付、平台审核、次日账单和业务验收仍以实际完成为准。

## 第一条垂直业务闭环

授权后的首个12小时不按“先把所有后台写完”推进，而是优先贯通：

> 后台创建学校、班级、课程、价格和团期 → 家长选择团期并添加多个孩子 → 服务端计算金额并生成订单 → 模拟支付成功 → 后台生成已缴费名单、人数和金额统计 → 导出Excel。

完成这条链路后，再扩展异常支付、真实微信支付、退款、分车和评价，避免三个前端与后端各自完成但无法联调。

## 工作分线

| 工作线 | 负责范围 | 文件边界 |
| --- | --- | --- |
| 平台与API | 数据库、权限、产品、团期、报名、订单、支付、部署 | `apps/api`、`deploy` |
| 家长小程序 | 课程、家庭成员、报名、订单和支付结果 | `apps/miniapp` |
| PC后台与执行端 | 配置、名单、统计、导入导出，随后扩展执行功能 | `apps/admin` |
| 共享契约 | 枚举、类型、校验规则和错误码 | `packages/contracts`，由集成负责人维护 |
| 备案与账号 | 小程序、腾讯云、域名、ICP、微信支付 | 平台后台操作，不提交密钥到Git |
| QA与发布 | 金额、幂等、权限、授权、真实设备和回归 | 各模块测试及 `.omo/evidence` 本地证据 |

同一时间运行三条代码线：平台/API与共享契约、家长小程序、PC后台与执行端。QA、许可证和安全复核可与代码线并行，但共享契约、数据库迁移和支付状态机仍由同一集成入口合并，避免并行产生两套业务事实。

## 连续执行方式

1. `T0`开始前：保存已审定基线，确认无未处理冲突，读取当前范围和共享契约。
2. 开发中：每项任务使用独立分支或Git worktree；一个分支只承担一个可验收结果。
3. 合并前：运行类型检查、单元测试、接口测试、构建和提交保护；前端任务增加真实浏览器/开发者工具检查。
4. 每4—6小时集成一次垂直业务链路，不等到模块全部完成后再联调。
5. 每个里程碑形成可回滚提交并更新任务状态和证据；生产数据、证书和本地日志不提交。

## 完成定义

“代码已生成”不算完成。任务只有在以下条件同时满足时才完成：

- 需求和不变量有明确依据；
- 代码、数据库迁移和共享契约保持一致；
- 成功、失败和权限场景均有自动验证；
- 真实页面或接口已经运行并观察到正确结果；
- 没有新增密钥、客户数据、大文件或许可证风险；
- 变更已形成可回滚的原子提交。
