# 启动修复与界面、需求、数据闭环核验

核验日期：2026-10-04。

后续实施更新：本报告发现的两项数据口径问题与四项P1界面建议已在同日完成修复、验证和新版本上传，详见[数据口径与界面完善交付](数据口径与界面完善交付-20261004.md)。以下保留实施前的审计事实和建议；外部服务与真实业务验收边界不因此自动改变。

本轮修改启动时旧登录页闪现的问题；其余界面、需求和跨端数据只检查并列出改进项。结论是：主要业务链已经建立，但不能认定所有需求都已落实并通过真实业务验收。本次发现两处可复现的数据口径错误，应优先于进一步美化处理。

## 1. 启动闪现修复

旧登录页收到跳转指令时，会先渲染“登录/注册、先逛逛”，等跳转完成才消失。这条路径已在真实 Vue 组件中复现，不以手机缓存解释。

本次移除这层废弃内容。冷启动访问旧路由时进入首页；订单、消息提醒等明确的登录入口继续打开现有身份资料、隐私、订阅流程；无效登录目标回首页，避免停在空白路由。默认首页没有改动。

产品修改仅三个文件：`apps/miniapp/src/pages/login/index.vue`、`apps/miniapp/src/manifest.json`、`apps/miniapp/tests/login-return.test.ts`。版本 0.3.36；API 和后台没有随本轮修改部署。

**发布结果：0.3.36 已重新上传，微信明确返回上传及预览成功。** 上传和预览大小一致，均为 1,719,572 字节；当前与上一版各 200 个冻结文件均通过摘要校验，临时网络设置已恢复。[新预览二维码](../.omo/evidence/startup-flash-audit-20261004/release/preview-0.3.36.jpg)。本次上传开发版本并生成预览，未设置后台体验版、提审或正式发布。

验证：旧代码的两项渲染回归先失败，修复后小程序 407 项测试通过，类型、lint、生产构建通过。真实浏览器 375/320 宽度下 29 个场景通过，逐帧观察超过 1 秒的跳转等待，未出现旧按钮。原生候选包及上传最终状态以[发布回执](../.omo/evidence/startup-flash-audit-20261004/release/release-verification.json)和[原生验证](../.omo/evidence/startup-flash-audit-20261004/native-receipt.json)为准。

原生补验实际确认了订单内部入口显示独立隐私弹窗，点击“仅浏览”返回订单；完整回归因微信开发者工具导航 RPC 超时未完成，记录为 PARTIAL，未写成全量通过。失败时的最新截图实际已经显示首页，工具没有返回导航完成结果。详见[原生验证边界](../.omo/evidence/startup-flash-audit-20261004/native-qa-boundary.md)。

浏览器中的导航和资料子组件使用明确标识的替身，原生验证中的微信授权与订单返回也使用测试夹具；这些不替代真实手机授权、真实资金或实际消息送达。

## 2. 两处已确认的数据问题

|优先级|触发与结果|影响及最小处理|
|---|---|---|
|P2：历史班级不一致|通过现有成员更新 API 修改已报名人员的年级、班级后，后台缴费名单和人数按当前班级筛选，名称却显示报名时旧班；出行名单使用报名快照。隔离执行出现旧班人数 1→0、新班 0→1，API 返回新班 ID 与旧班名。当前小程序界面没有换班入口。|经该 API 更新后，同一团期的缴费名单与分车、保险基础名单可能不一致。让该名单及统计统一优先采用报名快照，不改历史订单和真实人员数据；Excel 仅输出名称，不能将 API 的 ID 错位描述为 Excel 双列错误。|
|P2：累计支付少计|全额退款后，原支付记录变为 refunded；日期汇总只计算 succeeded，出现累计支付 1200→0 分，同时累计退款 0→1200 分。|不是退款执行金额出错，而是后台累计收付款展示失真。累计支付应包含后来全退的原成功支付，退款仍单列。保持按团期出发日期筛选的既有口径。|

两项都执行了当前模块或原始 SQL 的内存数据库复现，并比对已部署冻结代码和线上版本；没有操作生产订单，也没有将 SQLite 演示称为生产 MySQL 全链验收。复现脚本及详细源码位置见[接口闭环审计](../.omo/evidence/startup-flash-audit-20261004/api-closure-audit.md)。本轮未顺带修改这两处后台逻辑。

## 3. 需求是否严格遵循

本轮重读四份关键原件并核对摘要，按业务主题覆盖 96 项详细需求，结合后续明确决定核对当前实现。研学报名、团期定价、订单、微信支付、按人退款、逐人分车、保险交接记录、人工 A/B 评价等均有对应实现。历史已有真实小额支付和退款证据，本次没有重复支付或退款。

目前不能标记为全部验收的事项包括：

- 首批正式招生的学校、班级、价格、日期、告知书及合同正文是否由业务方核准。
- 付款人和实际出行人分别完成授权，并在手机实际收到报名、行前通知；微信接口受理不等于收到。
- 保险方接收正式名单、增减员及退保回执；退款成功不代表保险已处理。
- 第三方相册账号、真实活动链接、微信域名及导游上传、家长查看的实际贯通。
- 正式监护、肖像授权文本，以及相册范围和期限；登录隐私同意不能自动代替这些专项确认。
- 正式岗位账号权限、首个整团业务签收、执行原表和最终报告样式。

合同目前明确是家长本人阅读确认、待旅行社办理；人员变更审批目前是申请、审批及处理留痕。这些属于已经明确的边界，不能写成全部签章或正式换人自动完成。早期报价和参考图不叠加为本期全部义务，也不把已经确认的手动 A/B、按历史实付退款等规则重新列为待决定。

逐项依据、状态和待办见[需求核验矩阵](../.omo/evidence/startup-flash-audit-20261004/requirements-audit.md)。两处新确认的程序错误与外部未验收事项分开处理。

## 4. 界面与交互如何继续完善

案例参考包括确实获得红点 2023 品牌与传达设计奖的[佳士得微信拍卖小程序](https://www.red-dot.org/project/christies-live-auction-wechat-mini-program-66787)，以及[数字故宫官方案例](https://www.dpm.org.cn/classify_detail/257034.html)、[腾讯游云南案例](https://www.tencent.com/zh-cn/yunnan-province-leverages-big-data-and-cloud-computing-for-personalized-travel-experiences/)。后两者作为相关服务案例，不宣称获得同一奖项，也不把历史介绍当作 2026 最新界面实测。

现有绿色品牌、独立隐私和订阅弹窗、金额层次、取消支付入口继续保留。值得借鉴的是活动识别、下一步行动和后台处理效率：

|优先级|最小改进|验收方式|
|---|---|---|
|P1|后台合同选择团期时显示“学校、活动、日期”，编码为辅助。|同日不同校、同校不同课程均能直接辨认；保存前可确认目标团期。|
|P1|合同历史默认收起较早版本，让当前版本和编辑区先出现。|20 个版本仍可快速编辑，每个历史全文可查，旧订单合同不变。|
|P1|报名步骤名称准确对应“填写资料、核对信息、支付、完成”。|320/375 宽度可读；支付取消、失败时不会让家长误认为已完成。|
|P1|已付款订单突出“查看行前信息”，其余服务按任务分组。|未付款仍以支付和取消为主；已付款容易找到集合、车辆、联系人。|
|P2|首页避免同一课程的多个团期占满推荐，运营补齐可辨认的授权封面。|日期和价格仍来自同一团期，不混学校价格，不隐藏其他可报名日期。|
|P2|后台先突出可处理事项，再考虑趋势图。|每个数字能进入同口径列表；无数据、失败、无权限分开；没有真实时间序列就不绘制趋势。|

上述为有依据的改进建议，未在本轮顺带实施。图审查看十张近期截图并核对当前源码，已排除旧首页文案造成的误报。具体文件、成本估计和验收边界见[案例与界面审计](../.omo/evidence/startup-flash-audit-20261004/design-cases-audit.md)。

## 5. 下一阶段实施顺序

1. **修正两处数据口径。** 先增加换班、部分退款、全退、失败支付的回归，再局部修改 Roster 和日期统计；在隔离 MySQL 环境通过后台实际筛选、导出核对，确认小程序订单及历史快照不变。只部署对应文件。
2. **用同一个团期做端到端核验。** 后台设置学校、课程、价格、告知和合同；小程序浏览、登录、报名、签字、付款；后台核对订单与有效名单；再验证取消、按人退款、分车重确认及保险差异。记录同一订单/团期标识的流转，测试夹具与真实业务证据分开。
3. **补外部服务验收。** 明确参与验收的付款人和实际出行人，完成各自手机消息实收；由保险、相册对接人提供真实交接结果；核准专项授权文本与岗位权限。没有这些回执的项目继续标为未验收。
4. **实施四项 P1 界面优化。** 沿用现有颜色和组件，逐项小改，不改业务规则。小程序检查 320/375 宽度和大字号，后台检查常用桌面宽度以及多历史版本场景。
5. **形成可签认交付记录。** 按会议最终范围及后续确认，逐项记录已实现、已运行、外部已验收和仍待确认；以证据确认完成，不用一个“全部闭环”结论替代明细。

本轮检查不新增业务规则、依赖或服务，不修改真实数据，不撤回已提交版本，不自动提审或正式发布。
